## 设计取舍

**编码核心内联，不引第三方。** 项目的硬约束是「使用者零工具链、运行时只 ofa.js 一个依赖」，
二维码库不能走 npm，也不该为一个组件多加一个 CDN 请求。所以 ISO/IEC 18004 的编码器
（版本 1–40 的容量表、GF(256) Reed-Solomon、功能图案、8 种掩码按 N1–N4 罚分择优）整段写在
`qrcode.html` 的 `<script>` 里，约 9 KB 源码。**代价**是组件本体 24 KB（上限 40 KB 的大头都在这），
换来的是「引入一个 `<l-m>` 就完事」。

**矩阵正确性是离线验的，不进 CI。** 二维码错一位还是一张漂亮的图，但扫不出来 —— 而浏览器冒烟测试
判不了这个（页面里没有解码器）。写它的时候做过两轮交叉验证：① 与成熟的 `qrcode-generator`
（Kazuhiko Arase）逐位比对矩阵，覆盖 L/M/Q/H × 版本 1–40 × 中英 emoji × 随机文本；
② 把矩阵栅格化后交给 `jsQR` 解码，验证中文 / emoji 能原样还原。这两步是**一次性的**，
需要重跑时按这个思路临时搭（不要把第三方库塞进仓库）。

**只做 byte 模式。** 数字 / 字母数字模式能省下一点位，但省出来的通常只差一个版本，
换来的是一套分段选择逻辑与两份容量表（byte 模式的字符计数还会随之变化）。中文本来就只能走
byte，统一一条路更好维护。ECI 段也不加：主流扫码器（微信 / iOS 相机）对无 ECI 的 UTF-8 字节
都能正确识别，加了反而可能让老解码器把内容当 Latin-1。

**两个渲染器都常驻模板，靠 CSS 切换显示。** `canvas` 与 `svg` 同时存在于 shadow root 里，
`:host([renderer='svg'])` 决定谁可见 —— 切换渲染方式不销毁重建节点，也不会丢状态。
canvas 侧按 `devicePixelRatio`（上限 3）重建绘制缓冲，逐行把连续深色模块并成一条矩形。
svg 侧把整张图压成**一条 path**（`M x y h w v1 h-w z` 每行一段），模块再多也只有一个节点。

**canvas 全程在设备像素里算，不缩放坐标系。** 这里是唯一踩过的渲染坑：一开始用
`ctx.setTransform(dpr, …)` 让绘制代码按 CSS 像素写，边界 `Math.round` 到 CSS 整像素 ——
在 100% / 200% 缩放下没问题，但 Windows 常见的 125% / 150% 下 `CSS 整像素 × 1.25` 会落在
**半个设备像素**上，每个格子的边缘被抗锯齿糊成一条浅灰缝（实测 1.25 时 11.5% 的像素是灰的，
肉眼就是「黑格子之间有间隙」）。改成缓冲尺寸自己算（`Math.round(px × dpr)`）、
`setTransform(1,0,0,1,0,0)`、所有边界 `Math.round(n × 缓冲边长 / 总格数)`，
填充边界就永远落在整数设备像素上，灰像素归零（1 / 1.25 / 1.5 / 1.75 / 2 都验过）。

配套的两条约束：① **默认边长必须是 px 不是 rem** —— rem 跟着根字号走，一旦盒子尺寸与
绘制分辨率对不上，浏览器就要缩放位图，插值又会长出灰边；② 使用者自己把 `--mc-qrcode-size`
调得比 `size` 大时不可避免要缩放，用 `image-rendering: pixelated` 让它走最近邻，
宁可格子宽度差一像素，也不要灰缝（实测缩放下灰像素 0.01%）。

**图案只能是图片地址，不做插槽。** canvas 光栅化不了 DOM，插槽里放个 `mc-icon` 或文字就没法画进
位图；两条渲染路径要行为一致，所以只留 `logo` 一个属性收 URL / data URI。同理，
**跨域图片能画但会污染画布** —— `toDataURL()` 那时抛错，组件把它吞成空串（宁可导不出，也不要
「图显示不出来」）。同源图与 data URI 不受影响。

**图案比例夹在 0.05–0.4。** 再大就会盖到定位图案（三个角上的回字），那张码基本废了；
`logo-padding` / `logo-radius` 用 px 而不是比例，是因为留白要和图片的视觉重量对得上，
跟着二维码一起缩放反而不对。

**静区的单位是模块，不是像素。** `margin="4"` 在版本 3 和版本 30 上是不同的物理宽度，
但这正是规范要求的「4 个模块」—— 换成 px 就得反算模块边长，改 `size` 时还会失效。

**超容量不抛异常。** 内容超出上限时清空图形、给宿主标 `data-error="capacity"`，不写控制台。
二维码嵌在页面里，抛错只会打断调用方的渲染；标一个属性，需要时自己查。

**刻意不做事件。** 它是纯展示组件：没有交互、没有「扫码成功」这种浏览器层面拿不到的信息。
内容变了重画就完了 —— 与 `mc-progress` 同一条理由（属性即当前状态）。

## 令牌

| 令牌               | 默认    | 作用                                                                                    |
| ------------------ | ------- | --------------------------------------------------------------------------------------- |
| `--mc-qrcode-size` | `160px` | 宿主边长；写在宿主 style 上**优先于** `size` 属性（响应式用）。改它只改盒子，不重绘位图 |

## 相邻单元

- `mc-avatar`（[`../avatar/`](../avatar/)）：都是「一块固定边长的图形」，但 avatar 是装饰性的
  （加载失败还能落到首字母），qrcode 承载的是**数据** —— 画错一位就扫不出来，没有兜底。
- `mc-code`（[`../code/`](../code/)）：都是「同一份内容的另一种呈现」，code 把它原样摊开给人读，
  qrcode 把它编码成给机器读的格子。
