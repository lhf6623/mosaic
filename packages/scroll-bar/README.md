## 设计取舍

mc-scroll-bar — 滚动条

**为什么不是「给容器写一段 CSS」**：原生滚动条的样式是两套 API（Firefox 的
`scrollbar-width` / `scrollbar-color` 与 Chromium / Safari 的 `::-webkit-scrollbar`），
两边能表达的东西不一样（圆角、悬停、出现时机都缺），而且**占位的滚动条一出现就把内容挤窄**——
列表在「有几条」与「几十条」之间切换时，正文会横着跳一下。要一致、要不跳，就得自己画。

**但滚动本身必须是原生的**：宿主只做「尺寸 + 裁切」，真正滚的是里面那个 `.mc-viewport`，
它没被替换成 JS 滚动 —— 于是触摸惯性、键盘（Tab 进来 + 方向键 / PageUp/Down）、
锚点跳转、浏览器页内查找、`scroll-behavior: smooth` 全都照旧。**自己实现滚动的组件会在
这五件事上逐个翻车**，而它们加起来就是「滚动」这件事本身。

**条子是覆盖式的**（`position: absolute` 贴内沿，不占内容宽度）：这样溢出与否、
条子出现与否都不会改变内容的宽度 —— 也就是上面那个「横跳」被根治的地方。
代价是它盖住内容最右边那 `--mc-scroll-bar-w`（默认 10px）宽的一条，
所以长代码块 / 右对齐数字那一类内容要给自己的 `part="viewport"` 加内边距。

**滑块长度按比例，但有不小于 `--mc-scroll-bar-min-thumb` 的下限**：几千行里 1% 的滑块
只有半个像素 —— 看不见，也抓不住。下限一上，比例就不再严格线性（长列表里滑块会「提前」到顶），
这是所有自定义滚动条的共同取舍，选可抓取。

**`axis` 只有一条**（`y` / `x`，默认 `y`）：两条轴同时滚要画两个滑块、还要处理交叉角落，
接口与实现都要翻一倍 —— 而真实需求里它极罕见（真遇到就用普通 `overflow` 容器，
那边原生滚动条虽然丑，但两条轴是现成的）。

**`scroll` 事件从宿主上重发**：原生 `scroll` **不冒泡**，而 viewport 在 shadow 里面 ——
外面既拿不到它、也够不着它的监听点。不发这一次，使用者就只能靠 `MutationObserver` 之类的
歪路去感知滚动，所以这里主动重发一个 `bubbles` + `composed` 的 `scroll`。

**滚到底不锁住（刻意不写 `overscroll-behavior: contain`）**：第一版在 viewport 上写了 `contain`，
症状是「鼠标停在容器上时整页动不了」—— 实测容器滚到 602px 到底后再滚 300，页面纹丝不动，
使用者感受到的就是「滚动被锁住了」。默认的 `auto` 会把到头的滚轮交给外层，而这**正是项目自己的
口径**：外壳里那段「侧栏滚到底 → 接力给正文带」就是同一个规矩。真要「滚不出去」的场合
（弹层里的内滚区），使用者自己给 `::part(viewport)` 写 `contain` —— 那是使用者的选择，
不该是组件的默认。

**条子不吃指针（`pointer-events: none`）**：条子是 viewport 的**兄弟**节点、盖在最右边那
`--mc-scroll-bar-w` 宽的一条上 —— 它若接收指针，滚轮落在上面就到不了 viewport，
而**滚动条恰恰是大家最自然会去悬停的地方**：表现是「鼠标停在滚动条上滚不动，挪开一像素就能滚」，
也就是「时好时坏 / 不够灵敏」（实测：条子上 `scrollTop` 纹丝不动，旁边一格正常）。关掉指针让滚轮
穿透到底下的 viewport；滑块自己再把指针打开（要能拖），并在它上面单独把滚轮转给 viewport ——
那一小块（约 10×40px）挂非 passive 监听的代价可以忽略。

**拖拽要能被「取消」收掉**：只监听 `pointerup` 是不够的 —— 触控手势被系统收走、窗口失焦、
OS 接管时只会来 `pointercancel`，`pointerup` 根本不来。监听残留的后果是**之后鼠标一动内容就跟着跑**
（实测：`pointercancel` 之后仅移动鼠标，`scrollTop` 从 150 一路被拖到 600），使用者感受是
「滚动卡住了」。所以三条路都收：`pointerup`、`pointercancel`，外加移动时判一次
`event.buttons`（事件整个丢失时的兜底），并且新一次拖拽开始前先把上一轮收干净。

**无障碍只在「真的溢出」时才挂**：`tabindex="0"` + `role="region"` + `aria-label` 三件事
一起加、一起撤（不溢出时撤掉）。常驻的话，一个不滚的容器会变成一个按了没反应的 tab 停靠点，
比没有还糟。

**内容变化靠两层观察**：`ResizeObserver` 盯 viewport（宿主尺寸变了），再盯**插槽里被塞进来的
那些元素**（内容长高了）。只盯 viewport 的话，「往列表里追加一项」不会重算滑块长度 ——
而它恰恰是最常见的场景（`slotchange` 里重新挂观察对象）。

## 令牌

| 令牌                          | 默认                  | 作用                                               |
| ----------------------------- | --------------------- | -------------------------------------------------- |
| `--mc-scroll-bar-w`           | `10px`                | 条子（轨道）的厚 / 宽；滑块长度按它算比例          |
| `--mc-scroll-bar-min-thumb`   | `2rem`                | 滑块的**最小可抓长度**（长列表里比例会失真，见上） |
| `--mc-scroll-bar-gutter`      | `2px`                 | 滑块离宿主内沿的留白                               |
| `--mc-scroll-bar-radius`      | `--mc-radius-full`    | 滑块圆角                                           |
| `--mc-scroll-bar-thumb`       | `--mc-color-border`   | 滑块颜色（亮暗两套主题下都看得见，又不抢内容）     |
| `--mc-scroll-bar-thumb-hover` | `--mc-color-fg-muted` | 悬停在容器上时的滑块颜色                           |

**没有 `color` / `size` / `variant` 维度**：它不是内容，是一条滚动条 ——
「多粗、什么颜色」全都交给令牌（`size` 那种档位会让它和相邻容器的滚动条对不齐）。
