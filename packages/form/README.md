## 设计取舍

**没有 `<form>`，四件事全自己编排。** 原生表单那套（form owner、implicit submission、`FormData`）
要在**同一棵树**里才成立，而每个控件都有自己的 shadow root —— 这正是 `mc-radio`
「同 name 成组」失效的同一个原因。所以容器不假装有一个真表单，只做四件事：

| 能力       | 怎么做到                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 提交       | `click` 里用 `composedPath()` 认 `mc-button[type=submit]`；单行输入框里 <kbd>Enter</kbd> 也算（`textarea` 里是换行、不提交，按钮自己的回车走 click 那条路，不重复）                                                                                                                                                                                                                                                                                                                                                                                                           |
| 重置       | **不做**（见「刻意不做」）：数据驱动下"回到初值"是数据层的事，容器存一份快照就是第二个真相源                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| 取值       | 按**字段名**分组（先看 `mc-form-item` 的 `name`、再取控件自己的，两个都没有的不进值表）：单个开关类**问控件自己**（`formValue()`：写了 `checked-value` 就是「`checked-value` / `unchecked-value`」这一对，不写就是布尔）、同名多个给数组（勾上的取各自 `value`，没写 `value` 的按原生口径给 `'on'`），其余给字符串；禁用控件不算（同原生 `FormData`）；字段名带 `.` 时按路径嵌进对象                                                                                                                                                                                          |
| 校验       | 只跑 `rules` 里点名的字段：失败时**控件收 `invalid`、行收错误文案**；提交失败之后才跟着 `input` / `change` 实时更新。                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| 预留错误位 | `hide-error`（容器属性）只收起**文案**，那一格高度照留 —— 它是行间距，所以显示 / 隐藏文案都不改变表高。 **每一行**都常驻一行错误位（`.mc-error` 的 `min-height`）：有文案时装文案，没文案时它就是行与行之间的天然留白 —— 所以容器不给行距（`.mc-base` 没有 gap）、`.mc-body` 里也不留 gap，报错 / 收起都不改变任何高度。高度走 `--mc-form-item-error-h`。 `data-can-error`（来源 = 行自己的 `required` / `rules` + 容器的 `rules`，属性与 property 两条通道都算），CSS 据此给错误文案常驻一个行高 —— 报错 / 收起不再改变行高，整表不跳；没有规则的行不占位（`display: none`） |
| 清校验     | 全部：`form.clearValidate()` 或往容器派发冒泡的 `clear-validate`；**单个 / 几个**：`form.clearValidate('user.name')` 或事件带 `detail.fields` —— 删掉 `reset()` 之后，这是"清状态"的唯一入口。在飞的异步校验一并作废（按字段清就只作废那几个），否则清完又被晚回的结果标红                                                                                                                                                                                                                                                                                                    |
| 数据       | **不持有**：受控（控件绑 `sync:value="form.name"`）数据在你的 `data` 里；非受控（`default-value` / `default-checked`）真相在控件里。容器只从控件读值（校验与 `getValue()` 同一个口径）                                                                                                                                                                                                                                                                                                                                                                                        |

**字段名里的 `.` 是路径。** `getValue()` / `submit` 的载荷里，`data.name` 写成
`{data:{name:…}}`、`list.0.name` 写成 `{list:[{name:…}]}`（下一段是纯数字 → 这一段装数组）。
规则就这几条，都落在 `pathOf()` / `assign()` 里：**没有点 = 平铺键**（与原生 `FormData` 同一口径）；
**有空段（`a..b` / `a.`）或段名是 `__proto__` / `constructor` / `prototype` → 整条退回字面键**
（免得顺手改写原型，也免得半个名字被静默吞掉）；路径上撞到标量时**后者覆盖**（同 `lodash.set`）。
刻意**不做转义**（`a\.b` 表示字面点号）：多一条要学的规则，而真要用字面点号，把 `name` 换个写法
或在提交回调里摊平就行。

**跨标签只有三个宿主方法**（同 `mc-radio` 的 `syncGroupState`）：`mc-form` 调
`item.control()` 拿这一行的控件、`item.showError(msg)` / `item.clearError()` 落文案。
两个标签都不伸手进对方的 shadow root。

**命令式入口必须挂到宿主元素上。** ofa 的 `proto` 是**组件对象**的方法，外面拿到的 DOM 元素上
根本没有（实测 `el.getValue === undefined`）—— 所以 `validate` / `getValue` / `submit`
在 `ready()` 里用 `Object.defineProperty(this.ele, …)` 挂一遍，`form-item` 的三个接口同理。

**规则是对象数据，容器不内置「规则种类」。** 规则对象只认四个键（以后加能力 = 加键，
调用方式不改）：

| 键          | 值                                        | 说明                                                              |
| ----------- | ----------------------------------------- | ----------------------------------------------------------------- |
| `required`  | `boolean`                                 | 必填；空值口径见下（`mc-form-item` 的 `required` 属性是它的简写） |
| `validator` | `(rule, value, form) => …`                | 自定义校验；可以 async，返回值怎么解释见下                        |
| `message`   | `string`                                  | 失败文案；`validator` 只回 `false` 时用它，没写才用内置兜底       |
| `trigger`   | `'input' \| 'change' \| 'blur'`（或数组） | 平时什么时候提前校验；**不写 = 只在提交时跑**                     |

**规则写两处、各有两条通道**（属性装在标签上，property 挂在元素上）：

| 写在哪                                           | 属性通道（JSON 文本）                                                                            | property 通道（对象）                                    |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------ | -------------------------------------------------------- |
| `mc-form` —— **按字段名**，跨字段 / 集中配置     | `rules='{"username":[{"required":true,"message":"用户名不能为空","trigger":["input","blur"]}]}'` | `form.rules = { username: […], confirm: { validator } }` |
| `mc-form-item` —— **按位置**，连 `name` 都不用写 | `rules='[{"required":true,"message":"备注不能为空","trigger":"blur"}]'`                          | `item.rules = { validator: … }`                          |

一个字段的规则表按 **`required` 属性 → 行内 `rules`（属性 → property）→ `form.rules[字段名]`（属性 → property）**
的顺序拼，第一条失败胜出。

**函数不能靠绑定传，而且绑定的落点不稳定**：属性是文本，JSON 装不了 `validator`；模板里的
`:rules="某个对象"` 也不保证落到哪一侧 —— 实测**首屏直出**（地址栏没有 hash）时 ofa 可能直接把对象
赋给 `rules`（函数还在），**SPA 导航**进来时又会先 `JSON.stringify` 成属性文本（组件里 `this.rules`
拿到的是字符串，函数丢掉）。同一份代码两种结果，所以分工是：**声明式（`required` / `message` /
`trigger`）写属性，`validator` 一律挂载后用 property 补**。

**`validator` 返回什么都认**（写"返回不返回一句话"都舒服）：`''` / `undefined` / `null` / `true` = 过；
**非空字符串 = 失败且它就是文案**（比 `message` 优先，因为函数当场就说了）；`false` = 失败、文案取
`message` 或兜底；返回 `Promise` 时按上面同样解释 resolve / reject；抛异常 / reject 用
`error.message`（不静默、也不炸掉整轮）。

几条实现口径：

| 问题         | 口径                                                                                                                                                   |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 值给什么     | 与 `getValue()` 里该字段**同一份**（单个开关是布尔、同名多个是数组、禁用不算）—— 由 `collectFlat()` 一份数据同时喂给取值与规则                         |
| 谁被校验     | 规则表非空的**行**才动：`mc-form-item` 的 `name`（或裸控件自己的 `name`）决定它归哪条容器规则；没有规则的字段容器不碰（静态写上去的 `invalid` 也留着） |
| 空值口径     | 字符串 `trim()` 后为空 / 开关是 `false` / 同名组是空数组 —— 就这三条，想改口径用 `validator`                                                           |
| 多条规则     | 依次跑，**第一条失败胜出**，后面的不再跑                                                                                                               |
| 什么时候实时 | `trigger` 命中就报（**没有**「提交过一次才开始实时」这种隐藏门闩）；实时里异步晚回的结果会被丢掉（`_runs` 里的序号）                                   |
| 提交         | 提交时**所有**规则都跑，与 `trigger` 无关，所以不需要为它写什么                                                                                        |
| 同步 / 异步  | 统一异步：`validate()` / `submit()` 返回 Promise（同步规则也走同一条路）                                                                               |
| 键对不上字段 | 容器规则点了一个页面上不存在的字段名 → 没人执行；行内规则不发生这个问题（按位置绑定）                                                                  |

**一行里只有一列。** `mc-form-item` 的 body 是竖向的列（控件 + 错误文案），所以一个 item
放一个控件；要在一行里并排几个（一组 checkbox、两个按钮），自己包一层
`<div class="flex …">` —— 组件不去猜使用者想怎么排。

**认控件不能看「有没有 name 属性」。** ofa 会把声明过的字符串属性按空值写到宿主上（P32），
于是每个 `mc-input` / `mc-select` 都带着 `name=""` 坐在那儿 —— 初版按 `[name]` 选控件，
结果两个输入框挤进同一个 `""` 键、输出 `{"": ["1","2"]}`。现在的口径是：**先认值载体**
（真的有 `value` / `checked` 的元素，嵌套的只认外层），**再按「最近的 `mc-form-item` 的 name → 自己的 name」
取字段名，空名不进值表**；同一行里几个同名控件（一组 checkbox）照样合成数组。

**状态由容器落，判断由使用者给。** `validate()` / `submit()` 只负责把 `invalid` 挂上 / 摘掉
与写错误文案，「什么时候算错」一个字也不猜，「什么时候提前报」由 `trigger` 写在数据里 ——
容器里没有「提交过没有」这种隐藏状态（上一版那个门闩删掉了：有 `trigger` 的字段从第一刻起就报，
没有的只在提交时报）。

**校验态只有一处新东西：错误文案。** 控件的危险色还是它自己的 `invalid`（`mc-input` /
`mc-textarea` / `mc-select` / `mc-checkbox` 声明了它）；**`mc-switch` 与 `mc-radio-group`
没有 `invalid`**，那两个只有文案与 `data-invalid`（这一行自己的状态）能表达失败 —— 要补的话
是那两个单元的接口问题，不在这里绕。

**排布不内置：多列交给 `mc-grid`。** 容器上**没有** `layout` 这类维度 —— 几列、哪一格跨几列，
都是栅格（[`../grid/`](../grid/)）的活，表单只要把 `mc-form-item` 放进 `mc-grid-item` 就行
（文档页「栅格排布」那个演示）。`mc-form` 自己只把内容竖着叠成一列（`.mc-base`），
行与行之间的留白由每一行**底部的错误位**撑（见下），容器不另给行距；一行内部也固定是「标签在上、控件在下」。

真要把某一行改成标签在左（少见的排法），走**内部样式**：`mc-form-item::part(base) { flex-direction: row }`
配上 `::part(label) { width: 6rem }` —— 容器不为这一种长相再开一个属性。

**间距靠自定义属性继承**（同 `mc-radio-group`）：`--mc-form-item-gap` 的**默认值写在
`mc-form` 的 `:host` 上**，子项继承；`--mc-form-item-error-h`（行间距的实际来源）由行自己读，
默认值写在 `form-item.html` 的 `.mc-error` 上。⚠️ 容器那一个变量 `form-item.html` 的 `:host` **不能**
写默认值 —— 写了就盖掉继承，使用者在容器 `style` 上的覆写永远到不了。

**渲染完全由 data 驱动**（ofa 的 MVVM）：标签是 `{{label}}`、错误文案是 `{{error}}`（`showError()` 只写数据，
不碰 DOM），脚本里没有一句 `textContent`。⚠️ 因此 **DOM 更新落在下一拍** —— `await form.submit()` 之后读文案没问题，
但同步派发 `clear-validate` 后立刻读 DOM 会读到旧值（状态本身是同步的）。

**`data-has-label` / `data-required` / `data-invalid` 是脚本镜像的宿主属性**（P32 / P33）：ofa 会把声明过的字符串属性
（`label=""`）写到宿主上，「属性在不在」不能当条件；错误文案则要求「常驻 DOM + 属性显隐」（P10）。

**刻意不做**：**不内置重置**（受控时代替做法是换一份数据 —— `this.form = structuredClone(this.initial)`，
绑定自动推回控件；非受控时代替做法是自己把控件改回去。容器一旦为了 `reset()` 存一份"挂载那一刻"的快照，
它就有了第二份数据，与我们"容器不持有数据"的前提直接冲突）；**不做「把一份对象交给表单」的入口**
（曾经的 `form.model`：ofa 的 `:model="form"` 落点不稳定 —— 首屏直出可能是对象、SPA 导航时是 JSON 文本，
不能当契约；数据留在 `data` 里让控件直接绑）；往规则对象里再塞内置种类（`pattern` / 长度 / 数值区间……现在只有 `required` 一个
声明式快捷键，其余全写 `validator`；将来真需要就再加一个键，调用方式不变）；整表 `disabled`
（要改使用者轻 DOM 的属性，与 mc-form-item 的「控件是谁写的就归谁」冲突 —— 需要就逐个控件写 `disabled`）；
失败时把焦点跳到第一个错误字段（跨 shadow 的 `focus()` 不可靠，而伸手进控件 shadow root 是本库的禁区）；
真提交（不碰网络、不建 `FormData`）。

## 令牌

| 令牌                     | 默认                   | 作用                                                                                 |
| ------------------------ | ---------------------- | ------------------------------------------------------------------------------------ |
| `--mc-form-item-error-h` | `var(--mc-text-xs-lh)` | **每一行底部错误位的高度**（也就是行与行之间的留白）；文案常换行、或想松一点，往上调 |
| `--mc-form-item-gap`     | `var(--mc-space-2)`    | 标签与控件之间的间距（控件与错误文案之间**不留**：见「预留错误位」）                 |

## 相邻单元

- 栅格（[`../grid/`](../grid/)）：**多列表单就套它** —— `mc-grid` 定列数与间距、`mc-grid-item` 定跨几列，
  `mc-form-item` 放进格子里；容器自己不提供排布维度。
- 控件那一批（[`../input/`](../input/) / [`../textarea/`](../textarea/) / [`../select/`](../select/) /
  [`../checkbox/`](../checkbox/) / [`../radio/`](../radio/) / [`../switch/`](../switch/) /
  [`../slider/`](../slider/) / [`../rate/`](../rate/) / [`../tree-select/`](../tree-select/)）：
  `mc-form` 只按 `name` + `value` / `checked` 读它们，**不认识**具体是哪个组件 —— 原生的
  `<input>` / `<select>` / `<textarea>` 一样能放进来。
- `mc-dialog`（[`../dialog/`](../dialog/)）：弹窗里的表单没有额外接线 —— 值都在轻 DOM 上，
  关掉弹窗（挂 `hidden`）不丢值。
- `mc-button`（[`../button/`](../button/)）：`type="submit"` 是这里的提交入口（`type="reset"` 容器不认）。
