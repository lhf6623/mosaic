加载条。默认钉在视口顶部（全局在忙），也可以放进容器（那一块在忙）；状态只有一个入口 `state`（idle / loading / done / error），收尾先滑到 100% 再淡出 —— 成功与出错走同一条路，只差一个填充色。

## 设计取舍

mc-loading-bar — 加载条

**状态只有一个入口：`state`（枚举）**。曾经这里是 `active` 布尔 + `error` 布尔两个属性，
于是必然要回答「两个都写了听谁的」，而它们本来就**不是两件事**：出错和成功走的是同一条收尾
（先滑到 100%，再淡出），差别只有填充色。所以现在是一维枚举：

    idle    不出现
    loading 在跑：出现 + 爬升
    done    成功收尾：滑到 100% → 淡出
    error   失败收尾：同上，填充色换成出错色

**函数入口与标签是同一个东西的两种写法**：`loadingBar.start() / done() / error() / idle()`
就只是往那条条子上写 `state`（与枚举一一对应，没有第二套状态机）—— 所以 `loading-bar.js`
不碰 DOM 结构、不写样式，`loading-bar.html` 一行都不用改。它接过来的是使用者自己写会很烦的
三件事：懒挂载、**等 ofa 的实例就绪再写**、以及**落到哪**。

落点分两种，一模一样地对应组件那两个 `position`：不给 `target` → 造一条挂
`document.body`，用默认定位（`fixed`、视口顶部）——**必须挂 body**：shadow root 里的
`position: fixed` 会被宿主的 `transform` / `filter` / `contain` 困住（design-spec 第七节）；
给了 `target`（元素或选择器）→ 在那个容器里造一条 `position="static"` 的、`prepend` 到最上沿，
与「在容器里写一个 `position="static"` 的标签」同义（**同样不去猜容器**）。
⚠️ `target` 只覆盖 static 那一种：「盖在容器上沿、不占布局」要给条子写内联 `position: absolute`，
而模块写不了使用者的内联样式 —— 那件事留给标签入口。
模块级那三个收尾函数只管**默认那条**，`target` 那一条只认 `start()` 返回的句柄；默认那条还没
出现过时它们是 no-op（免得打错目标时在视口顶部闪一条）。

为什么不直接 `el.state = 'loading'`：实测**只有属性通道能驱动**（property 写法属性不变、
条子不出现），而使用者得先自己找元素、再 `setAttribute` —— 还得自己保证落点上只挂一条。
**刻意不做计数 / 定时器 / Promise 包装**：「现在有几件事在忙、跑多久算太久」是使用者的业务；
条子只表达「整体在忙」，不替调用方记账（两件事同时在忙时，先结束的那次 `done()` 就会收尾）。

**为什么是字符串枚举，而不是两个布尔**：一个状态维度里混着「布尔 + 字符串」两种类型
（`active=false` 配 `color='danger'`），用起来既不对称、又要靠顺序去猜；枚举则是一处写清
「现在是什么状态」。**颜色不再是维度**：它直接跟着主题走（在跑 / 成功 = 主色，出错 = danger），
要换色就覆盖令牌 —— 少一个属性，也少一套「显式和默认谁压谁」的规矩。

**视觉全由 `[state]` 派生**：CSS 里没有第二个标记（没有 `[data-on]` / `[data-done]` 那种
JS 写的中间属性），换状态就是换选择器命中。脚本只剩两件 CSS 做不到的事：进 `loading` 时把
上一轮的宽度瞬间归零（否则它会从 100% 往回滑），以及维护「在跑」时的语义三连。

**爬升用 transition 而不是 animation**：这样中途被打断时，下一条 transition 会**从当前值**
接着走 —— 收尾天然「不闪回 0」，也不必去读动画值（CSS 读不到它，之前为此写过一段
「读 computed → 写内联 → 才摘动画 → 强制回流」的脚本，现在整段都不需要了）。

**「先到 100%，再消失」是串出来的，不是同时**：滑满与淡出各自有令牌
（`--mc-loading-bar-finish` / `--mc-loading-bar-fade`），而淡出动画带一个
**等于滑满用时的 `animation-delay`** —— 纯 CSS 串行，没有定时器。同时开始的话条子会在半路上
就淡没了（实测：694px 的容器里只走到 212px 就没了，根本看不出「到过 100%」）。

**代价是它一闪而过**，所以两件事得使用者接住：出错用 `danger`（或你更喜欢的色），
以及**真正留在屏幕上的失败提示交给页面自己的 `mc-message` / `mc-alert`** ——
这条子只负责「刚才那次失败了」这个瞬时信号。

**两种落点，一个组件**：默认 `position="fixed"` 钉在视口顶部，表达「整个应用 / 整条路由在忙」——
那种场景下**一页只能有一个**；`position="static"` 则把定位交回文档流：它就在你放它的那个容器里
占 2 / 4px、通宽，表达「这一块在刷新」。两者共用同一套状态机与动画（那部分与落点无关），
差别只有一条 CSS 规则。

**`static` 刻意不去猜容器**：不套 `absolute`、也不去找最近的定位祖先 —— 后者会让容器凭空多出
一条「必须 `position: relative`」的约束，而这种约束最容易在半年后被人悄悄改掉。要盖在容器上沿
就自己写内联 `position: absolute; inset-inline: 0; top: 0`：那是**使用者的布局决定**，
组件不该替他做（同 `mc-scroll-bar` 不替使用者猜高度）。

**为什么要有它（`mc-progress` 已经能画一条不确定态了）**：进度条是**内容里**的一个元素，
它占版面、属于某一块 UI；而「整页 / 整路由在忙」这件事不属于任何一块 —— 它得铺满视口、
浮在所有东西之上、且**只有一个**。两者的驱动源也不同：progress 由业务数据驱动（跑到 42%），
loading-bar 由「开始 / 结束」两个事件驱动（路由切换、一次全局请求）。所以不是一个东西的两种外观。

**`pointer-events: none` 写死在宿主上**：它横跨整个视口顶部。若默认能接收指针，
顶栏、弹层、按钮在它那 2~4px 高度上的点击会被整条吞掉 —— 而且这种坏法在视觉上完全看不出来。
所以这条不是「默认值」而是定义，使用者想改得显式覆盖。

**状态机在脚本里，样式只读宿主属性**：`[data-on]` = 出现并爬升，`[data-done]` = 收尾。
两个属性都是脚本按 `active` 的**变化**写的，而不是 CSS 从「没有 active」推出来的 ——
后者会让**每次加载页面**都自己播一遍收尾动画（首帧就是「没在跑」，看着像刚跑完）。
`attached()` 里那次 `syncActive(active, true)` 的 `immediate` 就是干这个的。

**爬升用一条长缓出动画，终点是 90%（`--mc-loading-bar-reach`）**：不确定态的经典做法 ——
爬得越慢越像「还在跑」，但**永远到不了 100%**，否则一到头就像卡住了。时长走
`--mc-duration-*`（`shadow-base` 在 `prefers-reduced-motion` 下把它们压到 1ms），
所以不能写死秒数。

**收尾为什么要脚本插一手**：想从「爬升动画的当前位置」平滑滑到 100%，而 **CSS 读不到动画值**
（`animation` 的值压得住内联 `width`）。所以顺序是：读 `getComputedStyle` 的当前宽度 →
写内联 → **才**摘掉动画（摘早了会闪回 0）→ 强制回流 → 写 `100%` 交给 `transition`。
换成 `CSS.registerProperty` 能让纯 CSS 做到，但那是**全局注册**，这个库不接受全局副作用。

**复位靠 `animationend`，不用定时器**：淡出时长是令牌（还能被压到 1ms），定时器必然对不上 ——
要么提前切断淡出、要么空等一段看不见的时间。监听时判了 `event.target`：爬升动画在内部那条
`.mc-bar` 上，它的 `animationend` 会冒泡到宿主，不判就会误触发复位。

**没有插槽、没有事件**：它只表达一件事（「整体在忙」）。要说更多就别用它 ——
内容里的进度用 `mc-progress`，需要文案就用页面自己的提示条。

## 令牌

| 令牌                      | 默认                                  | 作用                                                                             |
| ------------------------- | ------------------------------------- | -------------------------------------------------------------------------------- |
| `--mc-loading-bar-fill`   | `--mc-color-primary`                  | 在跑 / 成功的填充色：**默认就取主题的主色**，要换色覆盖它                        |
| `--mc-loading-bar-track`  | `transparent`                         | 轨道底色（深色主题下想露一条底就给它）                                           |
| `--mc-loading-bar-z`      | `--mc-z-toast`（1500）                | 层级。默认压在顶栏 / 弹层之上，低于 tooltip                                      |
| `--mc-loading-bar-creep`  | `calc(var(--mc-duration-slow) * 24)`  | 从 0 爬到 `reach` 的时长；减弱动效下自动压到 1ms                                 |
| `--mc-loading-bar-finish` | `calc(var(--mc-duration-base) * 1.2)` | 「滑到 100%」用多久。**同时是淡出的延迟** —— 两段串起来才是「先到 100%，再消失」 |
| `--mc-loading-bar-fade`   | `calc(var(--mc-duration-slow) * 1.2)` | 淡出用多久（在滑满**之后**才开始）                                               |
| `--mc-loading-bar-reach`  | `90%`                                 | 爬升的终点。**别写 100%** —— 那就成了「卡住」                                    |
| `--mc-loading-bar-error`  | `--mc-color-danger`                   | 出错收尾用的色：主题的 danger                                                    |

**`color` 也收 hex**（`<mc-loading-bar color="#ff6b35">`）：语义名仍走 CSS，hex 走
[`../boot/color-attr.js`](../boot/color-attr.js) 写 `--mc-loading-bar-fill`。只收 hex，
非 hex 一条警告、什么都不写。

## 相邻单元

- 与 [`mc-progress`](../progress/) 的分工：progress 在内容里、由数据驱动、可以有值；
  loading-bar 在视口顶部、由开始 / 结束驱动、只有不确定态 —— 两者不该同时出现。
- 与 [`mc-spinner`](../spinner/) 的分工：spinner 是**某一块**在等（它占版面），
  loading-bar 是**整体**在忙（它不占版面）。
