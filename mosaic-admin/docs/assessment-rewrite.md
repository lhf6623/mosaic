# 用 Mosaic 重写 ed-nextscm-web：可行性评估

> 评估对象：`D:\ed-nextscm-web`（Vue 2.6 + Element UI 2.15 的 ERP 前端，约 26 万行）
> 目标框架：`D:\mosaic`（ofa.js 上的免构建 Web Components 组件库，43 个组件单元，版本 0.0.0，无 tag）
> 新工程：`D:\mosaic-admin`（空目录）
> 评估时间：2026-11-16

---

## 0. 结论速览

| 问题                  | 结论                                                                                                      |
| --------------------- | --------------------------------------------------------------------------------------------------------- |
| 技术上能不能做        | **能做，但这不是"复制重写"，而是"边造框架边重写业务"**                                                    |
| 建议                  | **不要整站一次性重写**。先做 P0 技术验证（2 周），再"外壳 + 单模块试点 + 上游补组件"                      |
| 为什么要慎重          | Mosaic 缺的不是"皮肤"，是 ERP 赖以生存的**数据网格**与**控制族**；而目标项目每月还在改动近 400 个视图文件 |
| 1:1 对齐工作量        | **中性 30–40 人月**（乐观 18–25，悲观 45–55）；3 人团队约 12–18 个月                                      |
| 只做"外壳 + 试点模块" | 约 **9–14 人月**，3–4 个月能看到可上生产的第一块                                                          |
| 最大单点风险          | `mc-table` 是纯文本表格，**没有单元格自定义内容**；而项目有 **298 个列表页**全靠 `base-page` 的配置化表格 |
| 第二风险              | 浮层四件套依赖原生 `popover` + CSS 锚点定位 → **Chrome/Edge 125+**；企微内置浏览器可能直接打不开          |
| 第三风险              | 目标近 30 天改了 **395 个视图文件**；框架 30 天内改了 **43 份 api.md**，且无 semver —— 两边都在动         |
| 更省钱的替代          | 若真实目的是"Vue 2 已 EOL / 想要新 UI"，**迁 Vue 3 + Element Plus 大约只要 1/4–1/3 的工作量**，且不丢生态 |

一句话：**技术上可行，经济上现在做整站重写不划算。** 建议把它拆成"可验证的小步"：先证明三件事——目标浏览器跑得起来、一个真实列表页的迁移成本、大表格与长表单的性能；证明之后再谈全量。

## 2. 八处硬落差

### 2.1 数据网格：决定性缺口

`mc-table` 的全部能力（`packages/table/api.md`）：
`columns`、`striped`、`hoverable`、`bordered`、`size`、`loading`、`empty-text`；行/表头模板固定，**单元格内容是 `cellsHtml()` 拼出来的纯文本（转义后输出）**。

而 ERP 列表页需要（且项目已在用、来自 `base/page` + `base/edit-table` + vxe-table）：

| 能力                                                 | 现状（Mosaic） | 项目是否在用 | 影响               |
| ---------------------------------------------------- | -------------- | ------------ | ------------------ |
| 单元格自定义内容（按钮、标签、图片、链接、进度、树） | ❌ 纯文本      | ✅ 全量      | 列表页根本无法迁   |
| 复选选中 / 跨页保留 / 批量操作                       | ❌             | ✅           | 批量审批、批量删除 |
| 展开行                                               | ❌             | ✅           | 明细展开           |
| 合并单元格（`mergeConfig`）                          | ❌             | ✅           | 单据合并显示       |
| 固定表头 / 固定列                                    | ❌             | ✅           | 宽表               |
| 虚拟滚动（>20 行启用）                               | ❌             | ✅           | 500 条/页          |
| 排序 / 列筛选 / 列设置 / 拖拽列序                    | ❌             | ✅           | 列表页标配         |
| 行内编辑 + 单元格级校验                              | ❌             | ✅（89 处）  | 单据录入           |
| 行拖拽排序                                           | ❌             | ✅           | 排序维护           |
| 表尾合计                                             | ❌             | ✅           | 财务               |

**这不是"补个属性"的量级**：仅 `base/page` + `base/edit-table` 就有 4,400 行，背后还有 vxe-table 这种数万行的专业网格。要迁，必须先在 Mosaic 里造一个 ERP 级表格（或改造 `mc-table` 使其支持单元格插槽 / 行模板 / 选择 / 展开 / 合并 / 固定表头 / 虚拟滚动 / 排序筛选 / 行内编辑），**工作量和风险都远大于其余组件之和**。而且它一旦设计错了，"298 个列表页"全部返工。

> 顺带说清可行性：`<td>` 里放自定义元素技术上没问题（foster parenting 只影响 `<table>/<tr>` 的直接子元素）。所以这是"要重做"，不是"做不了"。

### 2.3 页面模型不同：Vue SFC → ofa 模板

这不是"换个标签名"，是**换一套模板语言与响应式模型**：

| Vue 2                                        | ofa（Mosaic 文档站）                                                          |
| -------------------------------------------- | ----------------------------------------------------------------------------- |
| `<template>` + `<script>` + `<style scoped>` | 单个 `.html`：`<template page>` + `<script>`（导出函数）+ `<style>`（shadow） |
| `v-if` / `v-show`                            | `o-if` / `o-if` 反向条件                                                      |
| `v-for` + `key`                              | `o-fill` + `fill-key`（`$data` / `$index` / `$host`）                         |
| `:prop` / `v-model` / `.sync`                | `:prop` / `sync:prop` / `attr:prop`（布尔**必须** `attr:`）                   |
| 具名/作用域插槽 `#default="{row}"`           | 命名 slot（**能力弱于 Vue 作用域插槽**）                                      |
| `computed` / `watch` / `methods`             | `proto` 方法 + `watch` + `data`（`$.stanz` 响应式）                           |
| `provide/inject`                             | 能力有限，靠属性或全局 store                                                  |
| Vuex                                         | `$.stanz` 全局 store                                                          |
| 事件 `@click` / `$emit`                      | `on:click` / `dispatchEvent`（`CustomEvent`）                                 |
| 组件注册 `components: {}`                    | `<l-m>` 或 `load()`（每个组件一个 HTTP 资源）                                 |

需要在 953 个 SFC 里改写的 Vue 专有写法（静态统计）：

| 模式                                       | 次数           | 改写难度                                                |
| ------------------------------------------ | -------------- | ------------------------------------------------------- |
| `v-model`                                  | **4,458**      | 中（受控/非受控语义不同，要人工判断）                   |
| `$refs`                                    | 1,687          | 低（`shadow.$()` / `.ele`）                             |
| `v-if`                                     | 1,050          | 低                                                      |
| `methods` 块                               | 906            | 低（换 `proto`）                                        |
| `async/await`                              | 856            | 无（语言层）                                            |
| `$emit`                                    | 756            | 低                                                      |
| Vuex map 系列                              | 630            | 中（store 重写）                                        |
| `.sync`                                    | 543            | 中                                                      |
| `watch`                                    | 502            | 低                                                      |
| `computed`                                 | 474            | 中（缓存语义没有直接对应物）                            |
| Element 校验 `rules`                       | 411            | 低（`mc-form` 支持 `validator`，但函数必须走 property） |
| 命名插槽                                   | 350            | **高**（作用域插槽是 Element 表格/表单的惯用法）        |
| `v-for`                                    | 104            | 低                                                      |
| `provide/inject`                           | 70             | 中                                                      |
| `$set` / `filters` / `mixins` / 自定义指令 | 40 / — / 8 / 2 | 中                                                      |

**没有 codemod**：模板结构、状态归属、插槽契约都变了，只能逐文件人工改写 + 回归。

### 2.4 路由与页面注册：从"构建期上下文"变成"运行期映射表"

现在：后端菜单下发 `componentPath`，前端用 webpack 的 `require(['@/views' + componentPath])` 动态上下文解析（`src/store/modules/permission.js`）。
改成 ofa 之后：**没有构建期上下文**，浏览器只能按 URL 取页面模块。因此必须：

1. 生成一份 `componentPath → 页面 HTML 地址` 的**静态映射表**（833 个页面，用 Node 脚本从目录扫出来，纳入 CI 新鲜度检查）；
2. 定死"后端菜单路径 ↔ 页面文件路径"的约定；
3. 处理现状里那些"构建期能力"：懒加载、chunk 拆分、hash 指纹缓存、`keep-alive`（标签页状态保持）、iframe 页、白名单路由的 query 解密、`_newTab/_tabTitle` 等内部参数。

其中 **`keep-alive` 要重点验证**：ERP 用户会在多个标签页之间来回切，Vue 的 keep-alive 保住了滚动位置与未提交的表单。Mosaic 文档站里没有"页面缓存/恢复"的先例或说明。如果 ofa 的 `o-app` 导航会重建页面，这是**产品级体验回退**，需要自己实现状态快照 ↔ 恢复。

### 2.5 无构建的代价（工程与交付）

| 现在（webpack）                                         | 换成 Mosaic 后                                                                                                     |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| 产物带内容指纹、`chunk-libs` 拆分、gzip 预压缩、preload | **源码直发**：缓存策略要靠服务器配；无 tree-shaking、无 chunk 合并；每页一个 HTML + 若干组件 HTML + CSS + 图标字体 |
| npm 依赖 + 版本锁                                       | 依赖要换形态：UMD 全局 / `esm.sh` / 本地 vendor 副本；**没有 lockfile 的依赖图**                                   |
| ESLint + Stylelint + TS（部分） + Prettier              | 只剩 Prettier + 可选 `tsc`（**`.html` 里的脚本查不到**）；模板无 lint                                              |
| `.env.development/staging/production` 三套环境          | 需要自己做运行期配置（`window.__APP_CONFIG__`）与代理（本地开发仍可起个 Node 代理）                                |
| sourcemap / 错误定位                                    | 源码即产物，定位容易；但**没有构建期错误拦截**，坏页面在运行时才炸                                                 |
| 首屏可控（`app.js` + vendor）                           | 进入模块时多次 RTT 取组件；内网可接受，弱网/首次明显                                                               |

不是"做不到"，而是**这些支撑件都要新写一遍**，并且要接受"没有类型与 lint 兜底的 20 万行前端代码"。

### 2.6 浏览器基线（可能是硬阻断）

- Mosaic 的 popover / dropdown / tooltip / **select** 依赖原生 `popover` + **CSS 锚点定位**：Chrome/Edge **125**、Firefox 147、Safari 26；作者明确写了**没有降级路径**（`docs/pages/platforms.html`）。
- 目标项目里有 `@wecom/jssdk`（企微扫码登录）、`utils/wechat-compat.js`（企微滚动条补丁）。

**必须先确认**：ERP 是否需要在**企微内置浏览器 / 老版 Chrome / 政企内网锁定版本浏览器**里使用。如果是，Mosaic 现版本会让"下拉选择"直接打不开 —— 这是任何工作量估算都无法吸收的方案性风险。

### 2.7 未发版 + 无 semver + 目标仍在动

- Mosaic：0.0.0、无 tag、`private: true`，README 自述"首次发布前 CDN URL 会 404"。消费方式只能是**仓库副本 / submodule / 本地 vendor**，没有版本锁。
- 近 30 天改了 43 份 `api.md`（组件属性、事件契约还在变，最近几条提交就在改 menu/breadcrumb/pagination 的契约）。你既是使用者又是上游需求方：**组件缺口要你去补，补完的接口还会被上游继续改**。
- 目标项目近 30 天改动 395 个视图文件。**重写期间旧系统继续长**，1:1 对齐的靶子每月扩大约 5%。

对策只有一条：**fork 到 `D:\mosaic-admin\vendor\mosaic` 固定 commit，自己掌握节奏；同时把通用改进回推上游**。否则你会同时被两边拖。

### 2.8 第三方生态替换

| 现有依赖                                                                                              | 在新栈里                                                             |
| ----------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| Element UI + vxe-table + vxe-pc-ui                                                                    | 必须全部替掉（见 2.1/2.2），其中 vxe-table 的能力**没人替你补**      |

| ---------------- | ------- | ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `src/api`        | 6,228   | **70–80%**         | 全是 `request.get/post` 函数，改成 `fetch`/`axios` 版本约 300 行的 `request` 适配层即可；但 `api/index.js` 耦合了 Vuex token、Element Notification、`process.env` |

### 4.2 为什么不是"照抄一遍"

1. **模板语言不同**：4458 处 `v-model`、350 处命名插槽要人工判断受控/非受控与作用域语义。
2. **能力缺口要先造**：没有网格，列表页无从下手；没有抽屉/远程搜索/上传，表单页无从下手。
3. **"看不见的 1,034 次提交"**：权限码、字段级校验、打印导出、审批流、字典、企微兼容、时区/金额精度 —— 这些边角在代码里，重写时不会自动跟过来，只能靠回归测试与业务验收捞。
4. **两边都在动**：每月要额外花 5% 精力追平旧系统新增/修复。

### 4.3 与"迁 Vue 3"对比（同一条产品路线的省钱选项）

| 方案                                                    | 工作量        | 保留生态                  | 风险                                   |
| ------------------------------------------------------- | ------------- | ------------------------- | -------------------------------------- |
| A. Mosaic 整站重写                                      | 30–40 人月    | ❌ 全换                   | 高（网格 + 浏览器 + 框架未定版）       |
| D. Vue 3 + Element Plus + vxe-table 4 + Vite            | **8–14 人月** | ✅ 生态、招聘、工具链全在 | 中（Vue 2→3 迁移的已知坑，机械但量大） |

## 5. 三条路线

### 路线 A：整站一次性重写 ❌ 不建议

优点：一次到位、不留双栈。缺点：18 个月内无法交付价值、需求漂移、框架 API 漂移、资金风险集中。**除非有多人团队 + 明确的产品 freeze 期，否则不要。**

### 路线 B：外壳 + 试点 + 上游共建 ✅ 推荐（如果确定要换栈）

1. **P0（2 周）技术验证**，7 个 spike，全部有通过标准（见 §6）。
2. **P1（3–4 周）可运行外壳**：登录、菜单、标签页、主题、权限、请求层、页面映射生成器 —— 让"空壳"能跑通一个真实接口。
3. **P2（与 P1 并行，4–8 周）组件补齐**：数据网格第一优先，其次 upload / autocomplete / drawer / tree；每补一个，回推上游一份 PR。
4. **P3（3–4 周）单模块试点上生产**：挑一个"列表 + 详情 + 表单 + 导入"齐全但字段少的二级模块（建议 `risk` 或 `product`，不要挑 order/finance），灰度给一个小组用。产出**每页人日基线**。
5. **P4 规模化**：以模块为批次迁移，路由级灰度 + 新旧并行；每批必须有业务验收清单。

### 路线 C：反向采纳（不重写，先在旧项目里用 Mosaic 组件）

Mosaic 组件是原生自定义元素，Vue 2 里可以 `Vue.config.ignoredElements` + `ref` 绑 property 使用。**2–4 人周**即可验证"这套设计在真实业务里好不好用"，且不承担重写风险。适合"想先摸清楚 Mosaic 是否合适"的阶段。
局限：会形成双 UI 体系；Mosaic 组件在 Vue 模板里传对象只能走 `ref`，写法很别扭。

## 8. 需要你确认的 6 件事

1. **目标浏览器**：是否需要在企微内置浏览器 / 客户现场老版 Chrome 里使用？（决定方案生死）
2. **真实动机**：是 Vue 2 EOL、视觉升级、还是"公司统一 UI 底座"？若只是前两者，路线 D/E 便宜 3–5 倍。
3. **交付期望**：有没有 deadline？能不能接受 12–18 个月不产出（或按模块灰度）？
4. **人手**：几个人、是否全职、有没有人愿意一起维护 Mosaic 上游（补组件、返 PR）？
5. **后端/接口是否冻结**：菜单、权限码、字典、导入导出模板在重写期间会变吗？
6. **框架归属**：Mosaic 是你自己/团队的项目吗？能否推动发 0.1.0 tag 并定 semver？若不能，是否接受 vendor + fork 维护？
